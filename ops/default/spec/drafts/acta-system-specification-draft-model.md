# Acta System Model

Status: Proposed

Scope: Durable event and query model owned by the Acta service. This model does
not authorize implementation.

Parent specification: [Acta System Specification](acta-system-specification-draft.md)

## 1. Purpose

This document defines the durable event types, value rules, identity rules,
ordering, deduplication, correction lifecycle, and storage format used by the
journal.

The canonical journal is an ordered set of monthly UTF-8 JSON Lines segments.
Derived indexes and caches are not canonical and must be rebuildable from those
segments.

## 2. Event types

The initial model has two event types:

- `milestone`: records one significant commit;
- `correction`: corrects or clarifies a previously published event without
  rewriting it.

Every line contains exactly one complete event object.

## 3. Common event fields

Every event contains these fields:

```text
schema_version    fixed string: acta/v1
id                EventID
type              milestone or correction
recorded_at       UTC timestamp
execution         optional ExecutionContext
```

Unknown fields must be tolerated by readers. Writers must not change the
meaning of fields defined by `acta/v1`.

### 3.1 EventID

`EventID` is a globally unique, time-sortable identifier. ULID is the initial
representation.

Rules:

- IDs are generated by the Acta service;
- IDs are never reused;
- lexical order normally follows creation order;
- timestamp ordering uses `recorded_at` as the authoritative value.

### 3.2 RecordedAt

`recorded_at` is an RFC 3339 timestamp normalized to UTC with sufficient
precision to order events created in the same second.

`recorded_at` is the publication time assigned by the Acta service. It is not
the Git author or committer time. Those values are stored separately in the Git
reference.

### 3.3 ExecutionContext

```text
harness           agent harness name
harness_version   optional harness version
model             optional provider-qualified model identifier
```

`execution` describes the agent environment associated with the significant
commit. It does not identify the Acta service. `harness` may identify a client
such as Codex, Pi, or Herdr. `model` may contain a value such as
`openai/gpt-5.6` when the recording client knows it reliably.

The recording agent integration supplies execution values automatically. Acta
must not infer them from parent processes. A manual recording may omit the
complete object. Execution values do not participate in event identity,
deduplication, or authorization.

Execution strings must be non-empty after trimming and must not contain
newlines, control characters, credentials, environment values, prompts, or
session identifiers. They are advisory provenance supplied by the client, not
trusted evidence of authorization or identity.

Session identifiers are not part of `acta/v1`. The initial product does not
persist durable session identity or per-session books. A later schema version
may add session provenance when a reliable cross-runtime identity exists.

## 4. Milestone event

A milestone event has this shape:

```text
schema_version
id
type              milestone
recorded_at
execution         optional ExecutionContext
repository        RepositoryReference
git               GitReference
note              optional SignificanceNote
```

Example:

```json
{"schema_version":"acta/v1","id":"01K1Z8V7BMMN6W7Y6R8QJHA9SS","type":"milestone","recorded_at":"2026-08-05T14:22:31.418Z","execution":{"harness":"pi","harness_version":"0.42.0","model":"openai/gpt-5.6"},"repository":{"name":"example","root":"/workspace/example","identity":"ssh://git@example.test/team/example.git","remote":"ssh://git@example.test/team/example.git"},"git":{"commit":"0123456789abcdef0123456789abcdef01234567","branch":"dev","subject":"feat: add reusable agent protocol","authored_at":"2026-08-05T14:18:03.000Z","committed_at":"2026-08-05T14:20:47.000Z","worktree_clean":true},"note":"Reusable protocol behavior across agent-enabled projects"}
```

## 5. RepositoryReference

```text
name              repository directory basename
root              absolute canonical path at recording time
identity          stable repository identity
remote            optional sanitized canonical remote URL
```

### 5.1 Repository identity

When a configured canonical remote is available, `identity` is its normalized,
credential-free URL.

Normalization must:

- convert supported SCP-like Git syntax to a canonical URL form;
- normalize redundant path separators;
- preserve host, effective port, owner path, and repository name;
- remove passwords, access tokens, and credential-bearing URL components;
- treat one optional `.git` suffix consistently.

When no usable remote exists, `identity` is a local identity derived from the
canonical repository root. Local identity is stable only while that path
remains stable.

The initial CLI should prefer `origin` when it exists. Supporting an
explicit canonical-remote configuration is deferred.

### 5.2 Root path

`root` is a location hint and provenance value. It is not the durable repository
identity when a remote identity exists. Retrieval must still return an event if
the recorded path no longer exists.

## 6. GitReference

```text
commit            full lowercase hexadecimal object ID
branch            optional branch name
subject           first line of the commit message
authored_at       Git author timestamp normalized to UTC
committed_at      Git committer timestamp normalized to UTC
worktree_clean    boolean
```

Rules:

- `commit` resolves from `HEAD` at recording time;
- detached `HEAD` is valid and produces no `branch`;
- `subject` must not contain a newline or control character;
- `authored_at` and `committed_at` derive from the selected commit and use RFC
  3339 UTC timestamps;
- `worktree_clean` describes the complete worktree at recording time;
- dirty state does not prevent recording because unrelated changes may remain;
- file names, status details, staged content, and diffs are not persisted.

The full commit object ID is canonical. Abbreviated hashes are display values
only.

## 7. SignificanceNote

`note` is optional UTF-8 plain text.

Rules:

- it is one non-empty line after trimming;
- it contains no control characters;
- it is at most 500 Unicode code points;
- it explains significance rather than restating metadata;
- it must not contain a credential or secret.

The service validates structure but cannot guarantee that prose contains no
secret. The agent remains responsible for content selection.

## 8. Milestone identity and deduplication

The milestone key is:

```text
(repository.identity, git.commit)
```

At most one milestone event may exist for a milestone key.

Before appending, the service checks for an existing key while holding the
journal write lock. A duplicate request returns the existing event. It does not
merge, replace, or append the supplied note.

Changing a published note requires a correction event.

## 9. Correction event

A correction event has this shape:

```text
schema_version
id
type              correction
recorded_at
execution         optional ExecutionContext copied from target
repository        RepositoryReference copied from target
git               GitReference copied from target
note              optional effective SignificanceNote
target_id         EventID
reason            SignificanceNote
```

Example:

```json
{"schema_version":"acta/v1","id":"01K1Z9D5R9F5J7Z7P4J8X0QKTS","type":"correction","recorded_at":"2026-08-05T16:04:18.031Z","execution":{"harness":"pi","harness_version":"0.42.0","model":"openai/gpt-5.6"},"repository":{"name":"example","root":"/workspace/example","identity":"ssh://git@example.test/team/example.git","remote":"ssh://git@example.test/team/example.git"},"git":{"commit":"0123456789abcdef0123456789abcdef01234567","branch":"dev","subject":"feat: add reusable agent protocol","authored_at":"2026-08-05T14:18:03.000Z","committed_at":"2026-08-05T14:20:47.000Z","worktree_clean":true},"note":"Apply the reusable protocol to supported agent workspaces","target_id":"01K1Z8V7BMMN6W7Y6R8QJHA9SS","reason":"Clarify the supported agent harnesses"}
```

Rules:

- `target_id` must identify the current effective event in one milestone's
  correction chain, including an event in an earlier monthly segment;
- the target event remains unchanged;
- `reason` explains why the correction exists;
- the correction request may provide a replacement note;
- the stored `note` is the replacement note when supplied and otherwise copies
  the target's effective note;
- the service copies `execution`, `repository`, and `git` from the target's
  effective view;
- a correction cannot change execution provenance, repository identity, or Git
  evidence;
- a mistaken repository or commit reference requires a new milestone event and
  a correction that marks the old event as erroneous.

Every correction is independently searchable and understandable without
following `target_id`. Readers produce an effective view by selecting the last
valid event in each correction chain. Raw export preserves every original event
and correction in journal order.

## 10. Physical storage

Configuration resolves under `$HOME/.config/acta/`. Persistent and
transactional files resolve under `$HOME/.acta/`. The canonical journal root is
`$HOME/.acta/events/`.

The journal is partitioned by the UTC year and month of `recorded_at`:

```text
events/<year>/<month>.jsonl
```

For example, an event recorded at `2026-08-05T14:22:31.418Z` belongs in
`events/2026/08.jsonl`.

The journal root, year directories, and segments must be accessible only to the
owning user. Each event is encoded as one compact JSON object followed by `LF`.
Writers must not emit comments, blank records, trailing commas, or a top-level
JSON array.

The ordered set of monthly segments is the sole canonical event store. The
segment selected by the service recording timestamp is the active append
segment. After the service begins writing a later month, earlier monthly
segments are immutable.

## 11. Append and locking lifecycle

One recording operation follows this lifecycle:

1. The CLI resolves Git metadata without changing the repository.
2. The service receives and validates the bounded record request.
3. The service acquires the journal write lock.
4. The service recovers any known pending operation.
5. The service generates `recorded_at` and the event ID, selects the monthly
   segment, validates its tail, and checks the global
   milestone key index.
6. The service prepares the complete event in memory.
7. The service writes and syncs one pending operation containing the target
   segment, original segment length, and complete event line.
8. The service appends the complete event and newline to the active segment.
9. The service syncs the active segment.
10. The service removes the pending operation.
11. The service updates its derived indexes and releases the lock.

If publication fails, the operation must expose an error and must not report a
new event ID as committed.

The pending operation resolves to `$HOME/.acta/pending.json`.

Only one pending operation may exist because the service serializes canonical
writes. Recovery may complete a missing append, accept an already complete
event, or replace a matching partial terminal prefix with the complete pending
event. Any other mismatch is corruption and blocks writes to the affected
active segment. The pending file and its parent directory are accessible only
to the owning user.

The initial concurrency contract targets local filesystems on one host. Network
filesystems and distributed locks are outside the initial model.

## 12. Ordering

Raw journal order is segment path order followed by append order within each
segment. UTC year and month path ordering matches `recorded_at` ordering.

Default user-facing chronological order is `recorded_at`, then `id`. Reports
may group by repository or local calendar date but must preserve deterministic
ordering within each group.

Report dates use an explicit timezone when supplied. Otherwise they use the
invoking user's local timezone. Stored timestamps remain UTC.

## 13. Query model

A query may contain:

```text
event_types       optional set
repository        optional name or identity
commit            optional full or unambiguous abbreviated hash
harness           optional execution harness
model             optional model identifier
text              optional text query
recorded_from     optional inclusive instant
recorded_to       optional exclusive instant
authored_from     optional inclusive Git author instant
authored_to       optional exclusive Git author instant
committed_from    optional inclusive Git committer instant
committed_to      optional exclusive Git committer instant
limit             required effective positive limit, maximum 1,000
order             ascending or descending
```

Text search initially matches normalized repository name, commit subject, note,
correction reason, execution harness, and model identifier. Harness and model
filters use normalized exact matching. Execution filters do not match events
that omit execution provenance.

Queries bounded by `recorded_at` read only the monthly segments that can overlap
the requested interval. Author or committer time filters may use a derived
index or scan canonical segments because storage is partitioned by
`recorded_at`. Queries without a time bound may also use the global derived
index or scan all canonical segments.

Query output contains:

```text
query             normalized effective query
events            ordered matching effective events
returned_count    number returned
truncated         whether additional matches exist
```

Default query output contains at most one complete effective event per
milestone correction chain. Each returned event retains its stored `type`, ID,
and correction fields. No repository, Git, note, or execution lookup is needed
to understand a returned correction.

Raw export is a separate operation and must not be the implicit behavior of a
search or report command. A query stops before its encoded response exceeds 8
MiB and sets `truncated` when matching events remain.

## 14. Derived data

The service maintains global event ID and milestone key indexes across all
monthly segments. An implementation may also create a search index, offset map,
or integrity cache. Derived data:

- is stored outside the canonical monthly segments;
- is not required to understand the journal;
- can be deleted and rebuilt without information loss;
- must not change event identity or correction semantics.

## 15. Integrity verification

Active verification parses the current monthly segment. Full verification
parses all canonical segments in path order and rebuilds the global invariants.

Verification checks:

- valid UTF-8 and one complete JSON object per line;
- recognized schema versions and valid event fields;
- segment placement derived from `recorded_at` in UTC;
- unique event IDs across all segments;
- unique milestone keys across all segments;
- valid Git author and committer timestamps;
- correction targets that identify the preceding effective event;
- correction execution, repository, Git, and note snapshots that match their
  target chain rules;
- deterministic event ordering.

Verification is read-only. It reports the segment, line, and byte offset of a
failure when available. It does not repair corruption. Narrow pending-operation
recovery under Section 11 is part of the append transaction and is not general
integrity repair.

The initial model does not require historical segment checksums. Scheduled
active verification and explicit or monthly full semantic verification are the
initial integrity mechanisms.

## 16. Model invariants

- The ordered monthly JSONL segments are the sole canonical event store in the
  initial product.
- The Acta service is the sole canonical journal writer.
- Every published line is a valid `acta/v1` event.
- Event IDs are unique.
- Milestone keys are unique.
- Git commit hashes are stored in full.
- Git author and committer timestamps are stored in UTC.
- Credentials are absent from repository references.
- Corrections append history and never rewrite it.
- Milestones and corrections are independently searchable without joining
  canonical events.
- Derived indexes are disposable.
- Completed monthly segments are immutable.
- A pending operation is recoverable state, not a published event.
- Execution harness, harness version, and model are optional provenance, not
  business identity.
- Acta service identity and version are not repeated in canonical events.
- No event contains a prompt, transcript, diff, file contents, or hidden
  reasoning.
