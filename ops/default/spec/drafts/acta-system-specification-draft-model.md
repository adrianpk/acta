# Acta System Model

Status: Proposed

Scope: Durable event and query model owned by the Acta service. This model does
not authorize implementation.

Parent specification: [Acta System Specification](acta-system-specification-draft.md)

## 1. Purpose

This document defines the durable event types, value rules, identity rules,
ordering, deduplication, correction lifecycle, and storage format used by the
journal.

The canonical journal is a UTF-8 JSON Lines file. Derived indexes and caches are
not canonical and must be rebuildable from that file.

## 2. Event types

The initial model has two event types:

- `milestone`: records one significant commit;
- `correction`: corrects or clarifies a previously published event without
  rewriting it.

Every line contains exactly one complete event object.

## 3. Common event fields

Every event contains these fields:

```text
schema_version    fixed string: acta/v1
id                EventID
type              milestone or correction
recorded_at       UTC timestamp
producer          Producer
```

Unknown fields must be tolerated by readers. Writers must not change the
meaning of fields defined by `acta/v1`.

### 3.1 EventID

`EventID` is a globally unique, time-sortable identifier. ULID is the initial
representation.

Rules:

- IDs are generated by the Acta service;
- IDs are never reused;
- lexical order normally follows creation order;
- timestamp ordering uses `recorded_at` as the authoritative value.

### 3.2 RecordedAt

`recorded_at` is an RFC 3339 timestamp normalized to UTC with sufficient
precision to order events created in the same second.

The original commit time is not used as the recording time. Git commit dates
may be retained as derived Git metadata in a future schema version.

### 3.3 Producer

```text
name              fixed string: acta
version           Acta service semantic version
runtime           optional agent runtime label
```

`runtime` may identify a caller such as Codex or Pi when reliably provided. It
must not be required for event identity, retrieval, or correctness.

Session identifiers are not part of the settled durable model. The parent
specification leaves durable session identity and per-session books open. A
planning decision must resolve that boundary before adding session fields.

## 4. Milestone event

A milestone event has this shape:

```text
schema_version
id
type              milestone
recorded_at
producer
repository        RepositoryReference
git               GitReference
note              optional SignificanceNote
```

Example:

```json
{"schema_version":"acta/v1","id":"01K1Z8V7BMMN6W7Y6R8QJHA9SS","type":"milestone","recorded_at":"2026-08-05T14:22:31.418Z","producer":{"name":"acta","version":"0.1.0","runtime":"codex"},"repository":{"name":"example","root":"/workspace/example","identity":"ssh://git@example.test/team/example.git","remote":"ssh://git@example.test/team/example.git"},"git":{"commit":"0123456789abcdef0123456789abcdef01234567","branch":"dev","subject":"feat: add reusable agent protocol","worktree_clean":true},"note":"Reusable protocol normalization across agent-enabled projects"}
```

## 5. RepositoryReference

```text
name              repository directory basename
root              absolute canonical path at recording time
identity          stable repository identity
remote            optional sanitized canonical remote URL
```

### 5.1 Repository identity

When a configured canonical remote is available, `identity` is its normalized,
credential-free URL.

Normalization must:

- convert supported SCP-like Git syntax to a canonical URL form;
- normalize redundant path separators;
- preserve host, effective port, owner path, and repository name;
- remove passwords, access tokens, and credential-bearing URL components;
- treat one optional `.git` suffix consistently.

When no usable remote exists, `identity` is a local identity derived from the
canonical repository root. Local identity is stable only while that path
remains stable.

The initial CLI should prefer `origin` when it exists. Supporting an
explicit canonical-remote configuration is deferred.

### 5.2 Root path

`root` is a location hint and provenance value. It is not the durable repository
identity when a remote identity exists. Retrieval must still return an event if
the recorded path no longer exists.

## 6. GitReference

```text
commit            full lowercase hexadecimal object ID
branch            optional branch name
subject           first line of the commit message
worktree_clean    boolean
```

Rules:

- `commit` resolves from `HEAD` at recording time;
- detached `HEAD` is valid and produces no `branch`;
- `subject` must not contain a newline or control character;
- `worktree_clean` describes the complete worktree at recording time;
- dirty state does not prevent recording because unrelated changes may remain;
- file names, status details, staged content, and diffs are not persisted.

The full commit object ID is canonical. Abbreviated hashes are display values
only.

## 7. SignificanceNote

`note` is optional UTF-8 plain text.

Rules:

- it is one non-empty line after trimming;
- it contains no control characters;
- it is at most 500 Unicode code points;
- it explains significance rather than restating metadata;
- it must not contain a credential or secret.

The service validates structure but cannot guarantee that prose contains no
secret. The agent remains responsible for content selection.

## 8. Milestone identity and deduplication

The milestone key is:

```text
(repository.identity, git.commit)
```

At most one milestone event may exist for a milestone key.

Before appending, the service checks for an existing key while holding the
journal write lock. A duplicate request returns the existing event. It does not
merge, replace, or append the supplied note.

Changing a published note requires a correction event.

## 9. Correction event

A correction event has this shape:

```text
schema_version
id
type              correction
recorded_at
producer
target_id         EventID
reason            SignificanceNote
replacement_note  optional SignificanceNote
```

Rules:

- `target_id` must identify an earlier event in the same journal;
- the target event remains unchanged;
- `reason` explains why the correction exists;
- `replacement_note`, when present, is the corrected significance note;
- a correction cannot change repository identity or Git evidence;
- a mistaken repository or commit reference requires a new milestone event and
  a correction that marks the old event as erroneous.

Readers produce an effective view by applying valid corrections in journal
order. Raw export always preserves every original event.

## 10. Physical storage

The canonical path resolves as follows:

1. `$XDG_DATA_HOME/acta/events.jsonl` when `XDG_DATA_HOME` is set.
2. `$HOME/.local/share/acta/events.jsonl` otherwise.

The parent directory and journal must be accessible only to the owning user.

Each event is encoded as one compact JSON object followed by `LF`. Writers must
not emit comments, blank records, trailing commas, or a top-level JSON array.

## 11. Append and locking lifecycle

One recording operation follows this lifecycle:

1. The CLI resolves Git metadata without changing the repository.
2. The service receives and validates the bounded record request.
3. The service prepares the complete event in memory.
4. The service acquires the journal write lock.
5. The service validates the journal tail and checks the milestone key.
6. The service appends one complete event and newline.
7. The service flushes the append according to the host filesystem contract.
8. The service releases the lock.

If publication fails, the operation must expose an error and must not report a
new event ID as committed.

The initial concurrency contract targets local filesystems on one host. Network
filesystems and distributed locks are outside the initial model.

## 12. Ordering

Raw journal order is append order.

Default user-facing chronological order is `recorded_at`, then `id`. Reports
may group by repository or local calendar date but must preserve deterministic
ordering within each group.

Report dates use an explicit timezone when supplied. Otherwise they use the
invoking user's local timezone. Stored timestamps remain UTC.

## 13. Query model

A query may contain:

```text
event_types       optional set
repository        optional name or identity
commit            optional full or unambiguous abbreviated hash
text              optional text query
recorded_from     optional inclusive instant
recorded_to       optional exclusive instant
limit             required effective positive limit
order             ascending or descending
```

Text search initially matches normalized repository name, commit subject, and
note. Correction reasons are searchable when corrections are included.

Query output contains:

```text
query             normalized effective query
events            ordered matching effective events
returned_count    number returned
truncated         whether additional matches exist
```

Raw export is a separate operation and must not be the implicit behavior of a
search or report command.

## 14. Derived data

An implementation may create a search index, offset map, or integrity cache.
Derived data:

- is stored outside `events.jsonl`;
- is not required to understand the journal;
- can be deleted and rebuilt without information loss;
- must not change event identity or correction semantics.

## 15. Model invariants

- `events.jsonl` is the sole canonical event store in the initial product.
- The Acta service is the sole canonical journal writer.
- Every published line is a valid `acta/v1` event.
- Event IDs are unique.
- Milestone keys are unique.
- Git commit hashes are stored in full.
- Credentials are absent from repository references.
- Corrections append history and never rewrite it.
- Derived indexes are disposable.
- Agent runtime and terminal session details are optional provenance, not
  business identity.
- No event contains a prompt, transcript, diff, file contents, or hidden
  reasoning.
